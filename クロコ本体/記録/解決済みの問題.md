## 実装段階で判明した問題（2026-07-25）

### B. 設計の穴（実データを流して初めて表面化したもの）

1. **実装対象でないものが着手キューに入る**。
   実際に受験関係の資料メモを流したところ13件に分割され、うち3件
   （「概要と注意事項」「関連メモ（ソース）」「次に必要な情報」）は
   参照用であってタスクではなかった。しかし種別＝アイデアで未処理として並ぶため、
   実装フェーズが順番に拾って「実装しよう」としてしまう。
   → **対処済み**：種別に「資料」を追加し、実装フェーズは
   「予定」「資料」を着手対象から除外する（`NON_IMPLEMENTABLE_KINDS`）。
   Geminiには「迷ったらアイデアではなく資料に寄せる」と指示してある。

2. **AI作成が問題になる文書が、無人実装の対象に入りうる【重要】**。
   同じ13件の中に「やること：B. 出願書類（ドラフト作成）」が含まれていた。
   これが未処理のアイデアとして並ぶと、**クロコが起動して自己推薦書のドラフトを
   勝手に書き始めうる**。2.5章-8で「AI作成だと問題になり得る文書は無人実行の対象外」と
   決めていたが、その線引きがパイプライン側のどこにも実装されていなかった。
   受験関係のタスクを扱うと決めている以上、いつ踏んでもおかしくなかった穴。
   → **対処済み**：実装フェーズのプロンプトに「着手してはいけないもの」を明記した。
   本人名義で提出する文書（自己推薦書・志望理由書・出願書類・大学のレポート等）は
   本文を書かず `review` に回す。現実世界の行動が必要なもの（取り寄せ・郵送・予約）、
   課金・契約・外部送信を伴う操作も同様。
   ※ これは構造ではなく指示による制約なので、完全な保証ではない。
     より強く縛るなら種別や専用フラグで構造的に弾く必要がある（未着手）。

3. **分割の粒度は現状で良いと判断（確定）**。
   13件という数について検討した結果、見出し単位＝ほぼタスク単位に割れており、
   1行1タスクで独立したステータスが付く形は、第二段階でGemini APIに
   「次に何をするんだっけ」と引かせる用途にむしろ向いている、と結論した
   （1件にまとまっていると、どこまで終わったかを毎回本文から推測させることになる）。
   - ただし弱点が2つある：**前提が別行に散る**（「概要と注意事項」の注意書きは
     全項目に効くのに、1行だけ引くと落ちる）、**日程とタスクが離れる**
     （「第2次選考」の日付と「面接・口述対策」が別行）。
   - どちらも引くときに関連行をまとめて渡せば解消する。粒度を粗くして解く話ではない。
     第二段階の引き当て実装時に対応する（4章に再掲）。

### C. ドキュメントと実APIの食い違い（調べ直さないこと）

いずれも公式ドキュメントの記載どおりに書くと動かなかったもの。実APIで確認済み。

1. **Gemini の構造化出力**：`generationConfig.responseFormat.text.mimeType` は
   自由文字列ではなく **enum**。ドキュメントの例にある `"application/json"` は400になる。
   正しい値は **`"APPLICATION_JSON"`**（総当たりで確認）。
2. **Gemini の thinking**：`generationConfig.thinkingConfig.thinkingLevel`。
   旧2.5系の `thinkingBudget` とは併用不可（400になる）。
3. **Notion のDB配下ページ**：作成・クエリの親には `database_id` ではなく
   **`data_source_id`** を指定する（2025-09-03でdatabaseとdata sourceが分離された）。
   DBのIDからは `GET /v1/databases/{id}` の `data_sources[0].id` で解決できる。
4. **Notion のDB作成**：スキーマは `initial_data_source.properties` に入れる。

### D. 環境固有の問題

1. **NortonのSSL/TLSスキャンが全HTTPS通信を傍受している**。
   Nortonが動的生成するCA証明書の BasicConstraints が critical 指定されておらず、
   Python 3.13以降で既定有効になった `VERIFY_X509_STRICT`（RFCへの厳格適合チェック）が
   これを弾いて、あらゆるAPI呼び出しが `certificate verify failed:
   Basic Constraints of CA cert not marked critical` で失敗していた。
   → **対処済み**：このエラーのときだけ当該チェックを外して再試行する
   （`croco/httpjson.py`）。**証明書チェーンの信頼検証・ホスト名照合・有効期限の確認は
   引き続き有効**で、検証そのものを無効化しているわけではない。
   Norton側で暗号化接続のスキャンを切れば、厳格チェックのままで通るようになる。

2. **Notionの実体が二重にできていた**。本人がNotion AIと作った組
   （「未処理置き場（クロコ）」等）と、`setup_notion.py` が作った組
   （「未処理置き場」等）が並存し、`.env` は後者を指していたためメモを検出できなかった。
   → **対処済み**：置き場ページは本人作の組（メモが入っており、Notion AIへの
   指示先もそちら）、Inbox DBはスクリプト作の組（スキーマが一致）を採用。
   重複していた空のページ・DBは削除した。

3. **無人実行の設定ファイルは、壊れていても無言で無視される**。
   `claude -p`（非対話モード）では、検証に失敗した設定ファイルがエラーを出さずに
   無視される。つまり `croco_settings.json` を書き間違えると、
   **deny リストごと効かなくなったことに気づけない**。
   → 編集後は毎回 `claude doctor` で検証する（手順はREADME）。
   なお `claude doctor` に実際の検出能力があることは、わざと壊した設定で確認済み。

### F. スタートアップ起動の検証で見つかった問題（2026-07-25）

2.5章-2で確定した「PC起動時にスタートアップのショートカットから起動する」経路を
実際に走らせて検証したところ、**通常の実行では表面化しない問題が4つ**見つかった。
いずれも「起動時にだけ壊れる」種類のもので、放置すると
**毎朝サイレントに何もしないまま終わる**状態になっていた。すべて対処済み。

1. **`claude` が永続PATHに入っていない【致命的だった】**。
   `claude` の実行ファイルは `C:\Users\Seita\.local\bin\` にあるが、
   このディレクトリはUser・Machineどちらの永続PATHにも登録されておらず、
   対話セッション中しか解決できなかった。
   スタートアップから起動したプロセスでは `claude` が見つからず、
   **捕捉フェーズだけ動いて実装フェーズが毎回失敗する**という分かりにくい壊れ方をする。
   → 対処：PATHで見つからない場合に既定のインストール先を探すフォールバックを追加。
     確実にするなら `.env` の `CROCO_CLAUDE_COMMAND` にフルパスを書く。

2. **バッチファイルの日本語がパースを壊していた**。
   `croco.bat` に日本語のコメント・メッセージを書いていたが、cmd.exeは
   バッチファイルを実行中のコードページで読み直すため、`chcp 65001` と併用すると
   バイト位置がずれて以降の行の解釈が壊れる。実際、成功時にも `pause` が実行され、
   **起動のたびにコンソールがキー入力待ちで居座る**状態になっていた。
   → 対処：`croco.bat` はASCIIのみで記述する。日本語の出力はPython側に任せる。

3. **PC起動直後は回線がまだ上がっていないことがある**。
   通常のリトライ（数秒）では足りず、起動が回線確立より早いと
   何もせず終了してしまう。
   → 対処：処理を始める前にネットワーク疎通を最大120秒待つ。

4. **二重起動の防止がなかった**。
   実装フェーズは1回の起動で何十分も走りうるので、その最中に手動で起動すると
   同じアイテムを2つのプロセスが掴んで進捗ログが混ざる。
   スタートアップ起動と手動起動が重なるのは十分ありえる。
   → 対処：PIDを記録したロックファイルを持たせる。異常終了で残ったロックは、
     記録されたPIDの生死を確認して奪い取る（永久に起動できなくならないように）。

加えて、**実装フェーズの出力を貯め込まず1行ずつ流すように変更**した。
当初は出力をまとめて取得していたため、終わるまで画面に何も出なかった。
これは2.5章-2で想定した「動画を見ながら裏で実装が進むのを横目に見る」運用と
噛み合わないうえ、止め時の判断もできない。

### G. 実装フェーズの可視化（2026-07-25）

初回実行時、着手から完了まで画面に一切何も表示されなかった。
原因は `claude -p` の既定出力形式（text）が**完了までバッファされる**こと。
出力を1行ずつ流すようにコード側を直しても、この形式である限り効果がない。
無人実行とはいえ本人が横目で様子を見る前提（2.5章-2）なので、
進行が見えないと止め時の判断もできない。

→ 対処：`--output-format stream-json --verbose` に変更し、届いたイベントを
読める形に整形して出す（本文、ツール名と引数の要点、ツール結果の件数、完了時のターン数とコスト）。
ツールの引数は120字で切る（ファイル本文で画面が埋まるのを防ぐため）。
形式が想定と違っても落とさず生のまま出す（可視化のための処理で全体を落とすのは本末転倒なため）。

## 決着した論点（仕様書4章から移動）

- ~~Gemini APIのプロンプト文言そのもの~~ → **解決（2026-07-25）**：`croco/gemini.py` に実装済み
  （`SYSTEM_INSTRUCTION` と `RESPONSE_SCHEMA`）。モデルは3.5 Flashから **3.6 Flash** に更新（2.6章A-1）。
  実データで逐語転記・相対日付の解決・分割粒度・本人対応要否の判定が動作することを確認済み。
- ~~**「未処理置き場」「処理済み置き場」の実際のページ名・ID**~~ → **解決（2026-07-25）**：
  Notion上に「未処理置き場（クロコ）」「処理済み置き場（クロコ）」として作成済み。
  実IDは `%USERPROFILE%\.croco\.env` に記録（仕様書には秘密情報もIDも書かない方針）。
  Inbox DBは「クロコ Inbox」。**一時的に同名の組が二重に存在していた**経緯は2.6章D-2参照。
- ~~**Move Page API呼び出しの主体**~~ → **解決（2026-07-25）**：周辺のスクリプト側で実装した。
  Geminiの役割を「分割と転記だけ」に限定する方針と整合するため、この形で確定とする。
- ~~**実装フェーズが着手しない仕組みの強度**~~ → **おおむね解決（2026-07-25）**（2.6章B-2参照）。
  Geminiの出力に `needs_human` の判定を追加し、該当するものは**捕捉した時点で
  ステータスを「要確認」にして自動キューから外す**構造にした。実装フェーズの
  プロンプトにも同じ線引きを書いてあるが、そちらは指示であって保証ではないため、
  分類段階での隔離を主の防御としている。判定が欠落した場合は安全側（要確認）に倒す。
  実データで自己推薦書・志望理由書・活動経過報告書の3件が正しく隔離されることを確認済み。
  - **残る弱点**：判定そのものはGeminiが行うので、誤って `false` を返せば通ってしまう。
    完全な保証ではない。より強くするなら、キーワードによる機械的な二重チェックか、
    「アイデア」を既定で着手対象にしない（本人が明示的に許可した分だけ着手する）設計が要る。
- ~~**「予定」「資料」アイテムの最終ステータス**~~ → **解決（2026-07-25）**：
  ステータスに **「対象外」** を追加し、種別が予定・資料のものは捕捉時点でこれにする。
  - 「未処理」は実装フェーズの着手待ちフラグとして機能しているので、
    着手されようのないものをそこに置き続けるとキューが濁る。
  - かといって「完了」にすると、何もしていないのに完了したことになり、
    後から解析するとき（研究用にログを見る想定、2.5章-10）にデータが歪む。
  - 副次的な効果として、`pending_filter()` が拾わなくなるため、
    種別による除外と合わせて**二重の防御**になる。
