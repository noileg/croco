# クロコ：足りないもの一覧（2026-07-25時点）

第一段階のパイプラインのコードは一通り書き終わった状態。
ここから先、**動かすために足りないもの**と**まだ決まっていないこと**を種類別に並べる。

他のAIに相談する場合に単体で文脈が伝わるよう、各項目に前提も添えてある。
設計の経緯そのものは `クロコ_仕様書_統合版.md`、使い方は `README.md` を参照。

---

## 前提：クロコとは何か（相談相手向けの要約）

個人用のワークフロー自動化。スマホで思いついたことを寝かせずに実装まで持っていくのが目的。

```
スマホ（Notion AIチャット）
  └ 「未処理置き場のサブページにメモを作って」と毎回指示
       ↓
Notion「未処理置き場」の子ページ  ← 存在すること自体が「未処理」の印
       ↓  PC起動時に1本のコマンドが走る
  ① 捕捉：Gemini が話題の切れ目で分割（要約はしない・逐語転記）
          → Inbox DB に登録 → 成功したものだけ「処理済み置き場」へ移動
  ② 実装：Inbox DB から1件選び、Claude Code を無人で起動して実装させる
          → 進捗は Notion に書き戻す
```

環境：Windows PC 1台（メモリ8GB）、常時起動サーバーなし。作業の区切りごとに再起動する習慣があるので、
起動時トリガーだけで十分な頻度になる。無人実行中、本人は動画を見ていて張り付いてはいない。

設計の核：**失敗したら何もせず放置する。** 放置すれば次回のPC起動時に自然に再試行されるので、
専用のクラッシュ復旧処理を持たない。

## B. 実装が未着手の設計項目

### B-1. プロジェクトごとの git ブランチ／worktree 分離 【優先度：高】

**決まっていること**：無人実行中の失敗が main に波及しないよう、プロジェクトごとに
ブランチか worktree を切って作業させる、という方針だけは確定済み。

**今どうなっているか**：未実装。プロンプトで「`クロコ管轄プロジェクト` の下に専用フォルダを作れ、
その外には書くな」と指示し、`--add-dir` で範囲を絞っているだけ。

**決めないといけないこと**：
- プロジェクト1つ＝1リポジトリにするか、`クロコ管轄プロジェクト` 全体を1リポジトリにして worktree を切るか
- ブランチを誰が切るか（起動スクリプト側か、クロコ自身か）
- 無人実行中のコミットをどう扱うか（自動コミットさせるか、作業ツリーに置いたままにするか）

### B-2. プロジェクトレジストリ（どのフォルダで作業するかの判定） 【優先度：高】

**問題**：ブレストの内容から、それが「既存のどのプロジェクトの続きなのか」「新規に作るべきものなのか」を
判定する仕組みがない。これは仕様書4章に最初から残っている未解決項目。

**今どうなっているか**：プロンプトでクロコ自身に「対応するフォルダがあればそれを使い、無ければ作れ」と
丸投げしている。判断材料はフォルダ名だけ。同じプロジェクトに別名のフォルダが乱立する恐れがある。

**候補として考えていたこと**：`クロコ管轄プロジェクト` 配下に一覧・説明を持つマニフェスト
（プロジェクト名・概要・キーワード等のJSON/YAML）を置き、それと照合させる。形式は未着手。

**論点**：照合をGeminiにやらせるか、クロコにやらせるか。Inbox DB側にプロジェクト名の
プロパティを持たせるべきか（持たせるなら誰がいつ書くか）。

### B-3. 「要確認」になったことに気づく手段 【優先度：中】

**問題**：クロコが判断に詰まると Inbox DB のステータスを「要確認」に落とすが、
本人がNotionを見に行かないと気づけない。放置され続ける可能性がある。

**今どうなっているか**：ステータスが変わるだけ。通知はしていない。

**論点**：そもそも通知が要るか（Notionを見る習慣があるなら不要かもしれない）。
要るならNotion Automation（Businessプランに含まれる）でメール/Slack通知を出すのが素直か。

## C. まだ決まっていない論点

### C-1. 「予定」アイテムのステータスをどうするか

「予定」はカレンダー表示用で実装対象ではないため、実装フェーズは着手しない。
結果、ステータスが「未処理」のまま永久に残り、キューに溜まり続ける。

- 案1：そのまま（実装フェーズは種別で弾いているので実害はない。ただし見た目が汚い）
- 案2：捕捉時に「完了」にしてしまう（カレンダー表示は種別で絞られるので影響なし）
- 案3：「予定」専用のステータス値を足す

### C-2. Move Page API 呼び出しの主体

仕様書4章から残っている項目。Geminiに function calling でやらせるか、スクリプト側でやらせるか。

**現状**：スクリプト側で実装済み（`croco/capture.py`）。Geminiの役割を「分割と転記だけ」に
限定する方針と整合するので、この形で確定してよいと思われる。**要確認事項というより、
この実装で確定させてよいかの確認。**

### C-3. 実行結果（進捗ログ）が延々と伸びる件

同じアイテムを何セッションもまたいで続けると、進捗ログが際限なく伸びる。
仕様書では「現状の規模では問題にならないだろう、様子を見て必要なら対処」としている。

**論点**：上限を設けるか、古いログを畳むか、そもそも放置でよいか。

### C-4. 評価指標・ログの設計

「後でこのデータを解析して研究用プロジェクトの参考にするかもしれない」という動機がある。
現状は「ちゃんとログさえ取れていればいい」段階で、具体的な指標設計は後回しでよいとしている。

取れるようにしてあるもの：発話日時／処理開始日時／処理日時／試行回数／実行結果の履歴。
これで「発話→着手までのラグ」「着手→完了までの時間」「何ターンかかったか」「種別ごとの傾向」
「最終ステータスの分布」あたりは後から解析できる。

**論点**：この項目立てで足りるか。足りないなら早めに足しておかないと過去分が取れない。

## D. 実際に動かさないと分からないこと

コードは書けているが、認証情報が無いため一度も実地で確認できていない部分。
最初に動かすときはここを重点的に見る。

1. ~~**Gemini が本当に逐語転記するか**~~ → **確認済み（2026-07-25）**
   3話題を含む実際のブレスト調のログで検証したところ、**205字→205字で完全一致**。
   要約・言い換えは発生せず、言い淀み（「えーと」「んー」）もそのまま残った。
   相対表現の解決（「来週の火曜」＋「14時ね」→ 2026-07-28T14:00:00）も正しく動作。
   ※ 1例での確認なので、実運用で長いログ・話題が曖昧なログを流したら再確認する。

2. **話題の分割粒度が妥当か**
   細かすぎるとInboxが断片で溢れ、粗すぎると1アイテムに複数の実装対象が混ざる。
   上記の検証では3話題→3件と妥当だったが、判断に迷う入力での挙動は未確認。

3. ~~**Notion API のバージョン差異**~~ → **確認済み（2026-07-25）**
   `2026-03-11` で置き場ページ・Inbox DBの読み取り、データソースIDの解決とも動作。
   ただし**書き込み系（ページ作成・移動）はまだ一度も実行していない**。

4. **無人実行のパーミッションが想定どおり効くか**
   `--permission-mode auto` ＋ `croco_settings.json` の deny リストの二段構え。
   設定ファイルが検証を通ることは `claude doctor` で確認済みだが、
   実際に危険な操作がブロックされるかは動かさないと分からない。
   ※ `-p`（非対話）モードでは**検証に失敗した設定ファイルは無言で無視される**。
     `croco_settings.json` を編集したら毎回 `claude doctor` で確認すること（手順はREADME）。

5. **無人実行が実際どこまで進むか**
   1回の起動でどこまで行けるのか、進捗ログを頼りに次回ちゃんと再開できるのかは、
   何度か回してみないと分からない。

6. **メモリ的に動画視聴と両立するか**
   8GBで「動画を見ながら裏で実装」は画質を落とせば行けそう、という見込みで設計している。
   claude + python + ブラウザの同時稼働を実測していない。

## E. 意図的にやらないこと（第二段階以降）

混乱を避けるため明記しておく。以下は今回のスコープ外。

- ラズパイ／Dify／Cloudflare Tunnel／Syncthing を使う3層アーキテクチャ
- スマホからの対話ブレスト（STT→LLM→TTS 等）
- Webhookによるリアルタイムトリガー（常時起動サーバーが無いので意味を持たない）
- 定期実行（PCを頻繁に再起動する習慣があるので起動時トリガーだけで足りると確定済み）
- 自己推薦書のような、AI作成だと問題になり得る文書の作成
