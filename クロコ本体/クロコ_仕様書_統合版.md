## 1. 目的

- 一言で：認知的コスト・起動コストを下げるための、Notion＋クロコによる個人用ワークフロー自動化。
- PDFより：認知的コストと実行性の乖離による生産コストの低下を補う装置。原動力は2E／ギフテッドと呼ばれる特性のある人のためだが、組織への応用可能性もある。

## 2. 第一段階のスコープ（確定事項）

1. **範囲**：クロコ + Notion のみで構築する。ラズパイ／Dify／Cloudflare Tunnel／Syncthingは今回は使わない（将来の拡張候補として温存、詳細は3章）。
2. **Notion AIを契約する**（Businessプラン、$20/user/月）。
3. **Notion AIの位置づけ**：最終システムはNotion AIに依存させない。最終形は「クロコ＋Gemini API」で完結させる方針。Notion AIは契約から自己推薦書（大学出願書類）が書き終わるまでの、入口の便利機能という位置づけ。
4. **環境制約**：PCは1台のみ、常時起動サーバーは存在しない。ラズパイは未導入。
   → Webhookによるリアルタイムトリガーはこの環境では意味を持たないため保留。
5. **PCの運用スタイル**：使うたびにPCを再起動する。
   → 常駐タスクや個別登録プログラムの数を増やしたくないという強い選好がある。
   → 起動時トリガー（PC起動/ログイン時にまとめて処理を走らせる）方式で構わない。
6. **起動方法の方向性**：Notion取得・整形・クロコ起動を別プログラムとして個別登録せず、**1本のコマンド（パイプでつなぐ）**にまとめる方向。
   ※ 具体的なスクリプト名・CLIオプション・プロンプト文言などの実装細部は未決定。
7. **認証情報（APIキー等）の保管方法**：`.env`ファイルを、本プロジェクトフォルダ（Desktop配下）の**外**（例：`%USERPROFILE%\.croco\.env`）に置く方針。
   - 理由：このフォルダは現状OneDrive同期対象外だが、将来設定が変わった場合や、フォルダを人に渡す場合に備え、平文の秘密情報をプロジェクトフォルダ内に置かないため。
   - 1台の個人PC・多人数アクセスなしという環境を踏まえ、Windows資格情報マネージャー等への格上げは将来（サーバー常時公開等の段階）に見送る。
   - 具体的な配置パス・読み込み方法は実装時に決定。

## 2.5 第一段階のワークフロー（対話で追加確定した内容）

2章の確定事項をふまえ、以下のワークフローを合意した。

1. **入力・捕捉方法：確定**（web版Claudeとの別対話で詰めた内容を統合）。スマホでブレストしたアイデアは、以下の経路で必ずNotionを経由する。**生ログがGemini APIへ直接送られることはない**（この点、別対話中に一度AI側が誤った前提で回答したことがあるため、明示的に注意書きとして残す）。
   - Notion内に「未処理置き場」という親ページを作る。
   - Notion AIのチャットで捕捉する際は、毎回「このサブページにメモを作って」と明示的に指示し、**1回の捕捉＝1つの子ページ**として生成させる（Notion AIのデフォルトの保存先には頼らない）。
   - 経路：スマホ（Notion AIのチャット）→ Notion（未処理置き場の子ページ）→ PC（クロコが起動時に取得）。
2. **起動トリガー：確定**。PC起動時にクロコ（Claude Code）を立ち上げる方式でいく。定期実行（起動トリガーとは別に、一定間隔でも走らせるか）は**不要と確定**。理由：本人は作業の区切りなどでPCを頻繁に再起動する習慣があるため、起動時トリガーだけで実質的に十分な頻度になる。
   - 判断材料：このPC（メモリ8GB）で「YouTube動画を見ながら裏で実装させる」のは画質を落とせば行けそう、「重いゲーム（スタレ等）と同時」は厳しそう、という実地感覚から、**動画を見ながら裏で実装が進む運用を前提**にすることにした。
   - よって「趣味でPCを一瞬開いただけの時に邪魔」という懸念よりも、「起動したらそのまま実装が進む」ことを優先する判断。
3. **Gemini APIの役割：確定（当初の「要約」から修正）**
   - スマホから送られたブレストの生ログを、**話題の切れ目で分割するだけ**。本文は要約・言い換えせず**逐語転記**、タイトルは本文を指す短いラベルのみ（意味理解・仕様化はしない）。
     - 理由：Geminiが要約した時点で失われた情報はクロコ側で復元できない。非可逆圧縮を、何を作るか決まっていない段階で挟むのは危険なため。
     - **用語注意**：本人が会話中に「要約」と言っている箇所は、この「分割＋逐語転記のみ、非可逆圧縮はしない」方針と同じ意味で使っているだけで、方針変更ではない。「要約」という単語だけを見て圧縮処理だと解釈しないこと。
   - **処理〜書き戻しのフロー（確定）**：クロコ起動時のパイプの中で、Geminiが「未処理置き場」の子ページを一覧取得 → 各ページを分割・ラベリングしてInbox DBに登録 → **登録に成功したページのみ**、Notionの Move Page API（`POST /v1/pages/{id}/move`。2026年3月時点で追加、parentに`page_id`または`data_source_id`を指定。実在確認済み）で「処理済み置き場」という別の親ページの下へ移動する。
   - **未処理判定：特別なステータスフラグは不要**。「未処理置き場」の下に子ページとしてまだ存在しているかどうか、それ自体が未処理の印になる。Gemini呼び出しが失敗した場合は移動させず放置するだけでよく、「失敗時は何もしないことをデフォルトにする」という、Inbox DB側のステータス設計（10.）と同じ冪等性の原則がこちらの層にもそのまま適用される。
   - 分割・ラベリングした結果をNotionのInbox DBに登録する（1セッション＝1回のAPI呼び出しで、JSON配列として複数アイテムをまとめて返させる）。
   - **モデル：確定＝Gemini 3.6 Flash**（当初は3.5 Flashで確定していたが、実装時に現行GAが3.6になっていたため更新。2.6章A-1）。要約・分類・抽出用途ではFlash系がコスパ・性能とも妥当という調査結果（2026年7月時点）を踏まえて選定。本人としてはGemini自体の性能に一般的な不満（本質を突けない）があるが、「分割・転記のみで解釈はさせない」設計にしたことで、この用途ならFlashで十分という判断。実運用で精度不足を感じたら3.1 Proへの切り替えを検討。
   - **クロコ側のトークン消費への影響：問題なしと確認**。逐語転記でも1アイデアあたり数百〜数千トークン程度で、Claude Codeのコンテキスト規模からすれば無視できる量。またクロコは着手するアイテム単体（＋自分の進捗ログ）だけを読めばよく、DB全体を毎回読み込む設計ではないため、要約して圧縮する必要性自体が薄い。
     - 唯一気に留めるべきは、**実行結果（進捗ログ）が同一アイテムを何セッションもまたいで続けた場合に際限なく伸びること**。ただし現状の利用規模では大きな問題になるとは考えにくく、実装時に様子を見て必要なら対処する程度でよい。
   - （プロンプト文言の具体的な中身・スキーマ設計は実装時に決定。設計方針の詳細は3章「参考資料」参照）
4. **Notion Inbox DBの構造**：本人からクロコ（実装者）に設計を一任された。プログラムで扱いやすい形であれば形式は問わない、という条件のみ。
   - 実装時にクロコが提案する形で確定させる（本書では具体的なプロパティを先出ししない）。
5. **スコープの境界：更新**。当初は「パイプの担当はInbox DBへの要約登録までで、実際の実装作業はClaude Codeを普段どおり使うだけ（パイプの範囲外）」としていたが、**この整理は撤回**。
   - このプロジェクトの目的はそもそも実装を進めることなので、**起動時にクロコが立ち上がったら、そのままアイデアの実装に自動で着手する**、という前提に変更。
   - つまり「起動→（Inbox登録済みの）アイデアを拾ってクロコが実装を始める→本人は動画等を見ながらそれを横目に見ている」という、無人（本人が張り付いていない）実行が前提になる。
   - この変更により、**クロコの実行時オプション（許可ツール・パーミッションモード等、4章）の重要度が上がった**：本人が横で承認operationをするわけではないため、何らかの形で無人実行できる権限設定が必要になる。ここはまだ未決定。
6. **予定（スケジュール）のアプライ：実装方式が確定**。ブレスト中に日程が決まった場合、それをスマホから見えるようにしたい、という要望から出発。
   - 将来的にはDify運用開始後にそちらへ寄せる想定だが、それまでの間はNotionカレンダーで実装する方向は維持。
   - **仕組み**：Notionには「別の場所にpushする」という概念はなく、カレンダービューは同じDBの上に乗る表示形式の一つ。よって**別DBは作らず、同じInbox DBのままでよい**。
     - Inbox DBに「カレンダービュー」を1つ追加し、フィルタで**種別＝予定のみ表示**
     - カレンダー表示に使う日付は、処理ログ用の各種日時とは別に新設した**「予定日」プロパティ**（10.のDB構造参照）
   - これにより「Inbox DBとの関係」の論点は解消。予定アイテムは同じDB内で種別＋予定日により区別・表示される。
7. **無人実行で扱う想定のタスクの性質**：本人の想定用途は主に
   - Dify関連の日常用アプリ制作
   - 受験関係のタスク
   - 個人的に受注した小規模プロジェクト（マイコンでのデータロガー等の簡単なもの）
   であり、**「大きな事故さえ起きなければ強い権限は不要」という本人の判断**。パーミッションモードの検討はこの前提（＝重大事故の防止が最優先で、日常的な細かい承認は求めない）で進める（4章参照）。
8. **AI利用が問題になりうる文書の扱い**：自己推薦書のような、AI作成だと問題になり得る文書は**現時点ではAIに作成させる予定がなく、無人実行の対象外**。
   - ただし将来、大学のレポート等でAIを使う可能性はあるとのこと。その際の安全策として、GitHubやNotionでバージョン管理し、そこへのpushという形にする案が本人から出ている（まだ検討段階、決定ではない）。
9. **パーミッションモード：確定**。7・8を前提に、「日常操作は自動承認、真に危険な操作（`git push --force`／共有ブランチへの`git reset --hard`／プロジェクト外への書き込み・削除／`rm -rf`的な広範囲削除／外部送信系操作）だけ明示的に拒否する」方針で進める。
   - 拒否リストの具体的なパターン一覧（settings.jsonの記述等）は実装時に詰める。
10. **Notion Inbox DBの構造：たたき台を本人が提示、方向性は良好**

   | プロパティ名 | 型 | 値/選択肢 | 書き込み主体 | 備考 |
   |---|---|---|---|---|
   | タイトル | title | 自由記述 | Gemini API（自動生成） | 生ログの該当セグメントに対する自動ラベリングのみ。意味理解・仕様化はしない |
   | （ページ本文） | page content | 自由記述 | Gemini API | 生ログから該当セグメントを抜粋・転記。クロコが直接読んで解釈・実装する対象 |
   | 種別 | select | アイデア / 予定 / **資料** | Gemini API（作成時） | 実装対象（Inbox）か、予定アプライ対象かを区別。同一DB内で区別する方針で確定。「資料」は参照用で着手対象外（2.6章A-3） |
   | 予定日 | date | - | Gemini API（種別＝予定の場合） | **確定・追加**。予定そのものの日時（例：8/3に予約）を持つ専用カラム。他のdate系プロパティ（発話日時等）はすべて処理ログ用で予定の日時とは無関係なため、別途必要だった |
   | ステータス | select | 未処理 / 処理中 / 完了 / 要確認 / **対象外** | 作成時=スクリプト（種別と本人対応要否から決定）、以降=クロコ | 各処理段階が成功したことを確認してから変更。失敗時は変更せず残す（次回起動時に自然に再試行される）。作成時は、種別が予定・資料なら「対象外」、本人自身の対応が要るなら「要確認」、それ以外は「未処理」 |
   | 発話日時 | date | - | クロコ（Gemini呼び出しのスクリプト側） | **更新・前進**：以前は「Gemini自動化パイプラインができるまで空欄」としていたが、1.の捕捉フロー確定により前倒しできる。「未処理置き場」の子ページ自体がNotion AIとの対話でその場で作られるため、**その子ページの「作成日時」（Notion側が正確に記録）を、Inbox DB登録時にスクリプトがそのままコピーすればよい**。LLMに現在時刻を自己申告させる必要はない（Notion AIの時刻認識精度が信用できないという以前の懸念はこれで回避）。 |
   | 作成日時 | created_time | - | 自動 | Notion側のページ作成時刻。当面は発話日時の代用として扱う |
   | 処理開始日時 | date | - | クロコ（最初に未処理→処理中にした時） | 「発話から着手までのラグ」を後から測れるようにするための追加（**追加提案**） |
   | 処理日時（完了） | date | - | クロコ | 処理完了時に記入。処理開始日時との差分で処理時間を測れる |
   | 実行結果 | rich text | 自由記述（進捗ログ） | クロコ | セッションをまたぐ進捗の引き継ぎフック。gitのコミットメッセージのような、簡潔な進捗ログを都度追記していく形式で確定。ログの件数を数えれば後から「何ターンかかったか」も解析できる。追記の粒度・タイミングの実装細部は未定 |

   - 「失敗時は未処理のまま残す→次回起動時に自然に再試行」という設計により、**冪等性・エラーハンドリングの土台は解決済み**（4章の未決定事項から実質的に前進）。
   - **「処理中」ステータスの位置づけ：確定**。クラッシュ時の特別扱い（未処理に戻す等）ではなく、そもそも**「処理中」＝複数回の起動セッションをまたいで実装が進行中の状態**という位置づけ。実装は1回の起動＝1ターンとは限らず、対応（ターン）ごとに状況に応じて動的にステータスが更新される想定（1回の応対で1回更新、という粒度は本人の想定であり、実装時に検証）。
     - よって次回起動時は、**新規の「未処理」より「処理中」を優先して処理を再開する**という優先順位にする。これにより、通常の再開処理と、実行が中断された場合の復旧処理が同じ仕組みで自然に統合される（別途クラッシュ復旧ロジックを設ける必要がない）。
     - **進捗の引き継ぎ方法：確定**。実行結果（rich text）に、gitのコミットメッセージ的な簡潔な進捗ログを追記していく形式とする。次セッションはこれを読んでフックとして続きを実装する。追記の書式・粒度（1ターンごとか、まとめてか等）は実装時に決定。
   - **種別（アイデア/予定）プロパティ：確定**。同一Inbox DB内に混在させ、種別プロパティで区別する方針とした（別DBには分けない）。
   - **研究解析用のログ：方針確定（詳細は未定）**。本人より「後でこのデータを解析して研究用プロジェクトの参考にするかもしれない」という動機が示された（4章「評価指標・ログの取り方」と同根の話として統合）。
     - 現状のハードルは高くなく、「今はちゃんとログさえ取れていればいい」（詳細な評価指標の設計は後回しでよい）という前提。
     - この前提のもと、上表に**発話日時・処理開始日時を追加提案**した。これにより後から「発話→着手までのラグ」「着手→完了までの処理時間」「何ターンかかったか（実行結果ログの件数）」「種別ごとの傾向」「最終ステータスの分布」といった分析ができるようになる、という設計上の狙い。
     - ただし発話日時が実際に取得できるかは、スマホからの入力手段自体が未定なので未確定。
   - 残る論点（未確定のまま）：
     - 作成日時と発話日時のズレの扱い（発話日時が取得できない場合の代替を含む）
11. **Gemini APIプロンプト設計：方向性を確定（文言そのものは実装時）**
    - **呼び出し単位**：ブレスト1セッション＝API1回。生ログをまとめて渡し、JSON配列で複数アイテムを一括で返させる（アイテムごとに呼ばない）。
    - **出力方式**：構造化出力を使う。スキーマはfield単位で`description`を付け、プロンプト本文にスキーマを重複記載しない（重複は出力品質を落とすとGoogleが明記）。種別は自由文字列ではなく`enum`にして揺れを防ぐ。
      ※ 実APIでの正しいフィールド名は `generationConfig.responseFormat.text.{mimeType, schema}` で、`mimeType`はenum（`APPLICATION_JSON`）。当初想定していた `responseMimeType` / `responseSchema` は誤り（記録/解決済みの問題.md のC参照）。
    - **スキーマに含めないもの**：ステータス（常に"未処理"固定なのでスクリプト側でハードコード）、発話日時・処理日時・実行結果（クロコ側が書くものなので対象外）。
    - **現在日時はスクリプトから注入**：Notion AIの件で確認済みの通りLLMは現在時刻を知らないため、「来週の火曜」等の相対表現を予定日に変換するには必須。この注入日時は将来「発話日時」カラムにもそのまま使える。
    - **thinking**：3.5 Flashでは`thinking_budget`ではなく`thinking_level`。分割・転記に深い推論は不要なため`minimal`から開始し、精度が問題になれば上げる。
    - **temperature**：低め（0〜0.3）。抽出タスクなので創造性は不要。
    - これらはコスト最適化目的ではない（このボリュームではAPI従量課金・レート制限は無風であることを確認済み）。**目的は精度と、クロコが後で読む際の情報保存**のため。
12. **無人実行の安全対策：追加で確定**。9.（自動承認＋危険操作の拒否）に加え、実装時に以下も行う。
    - **Notion連携トークンのスコープをInbox DBのみに絞る**：ワークスペース全体ではなく、Notion Integrationの共有（Connect）をInbox DBだけに限定する。鍵の漏洩・バグ時の被害範囲をこのDBだけに閉じるため。
    - **プロジェクトごとにgitブランチ／worktreeを切って作業させる**：無人実行中の失敗がmainに波及しないよう、被害範囲をブランチ単位で最初から区切っておく。「危険操作の拒否」が行為ベースの防御なのに対し、こちらは範囲ベースの防御として別レイヤーで効く。
    - **同一アイテムの再試行に上限を設ける**：一定回数（実装時に具体値を決定、たたき台は3回）進捗がないまま繰り返したら、自動的に「要確認」に落として人間待ちにする。無限ループの防止。
    - **止め方の確認**：タスクマネージャーやターミナルを閉じる等、放置中に異常に気づいた際すぐ止められる手段を本人側で把握しておく（実装不要、運用上の確認事項）。
    - これらは**このクロコ・パイプライン自体を実装するタイミングで適用する対策**であり、今の時点（仕様検討中）で何かを設定するものではない。
13. **クロコ管轄プロジェクトの置き場所：確定**（実装前レビューで指摘した「どのフォルダに実装するか決める仕組みがない」への対応の第一歩）。
    - `プログラミング関係`直下は既存の雑多なプロジェクト（命名・日付ともに不揃い）が既に大量にあるため、混在させない。
    - `プログラミング関係`の子ではなく、**Desktop直下に新規の専用ディレクトリ「クロコ関係」を作る**（`プログラミング関係`は今後も雑に作ったものを入れる場所として維持）。
    - 構造：`クロコ関係/クロコ管轄プロジェクト/<プロジェクトごとのフォルダ>`。クロコが無人実装するプロジェクトは必ずこの`クロコ管轄プロジェクト`配下に作る。
    - **安全対策との連携**：12.の「プロジェクト外への書き込み・削除を拒否」の境界は、この`クロコ管轄プロジェクト`をルートとして定義できる（雑多な`プログラミング関係`の中で境界を引くより単純かつ堅牢）。
    - **二段階目を見据えた設計**：`クロコ関係`は`クロコ管轄プロジェクト`だけでなく、将来（第二段階）の同期・連携用フォルダ（例：ラズパイ/Dify等との連携フォルダ、サーバーに返す内容を入れるフォルダ等）も同じ階層に置く前提にしておく。具体的なフォルダ名・構成は未確定（3章「将来構想」のworkstation/history/output案が参考になる）だが、置き場所として`クロコ関係`直下を予約しておく。
    - **クロコ本体も統合：確定**。パイプライン自体のコード・本書（旧`プログラミング関係\クロコ`）も、`クロコ関係\クロコ本体\`として統合する。つまり最終形は：
      ```
      クロコ関係/
        クロコ本体/          … パイプライン自体のコード・本仕様書
        クロコ管轄プロジェクト/ … クロコが無人実装する個別プロジェクト
        （将来）連携・サーバー返却用フォルダ等
      ```
    - 内容は`クロコ関係\クロコ本体\`へコピー済み（2026-07-24）。旧`プログラミング関係\クロコ`は、セッションのハーネスがそのパスをアンカーとして固定していることと、Obsidian vaultとして開かれている可能性があることから、中身の削除は本人による手動対応に委ねている（4章「クロコ本体の移動」参照）。
    - **同日中の進捗**：セッションを`/cd`で`クロコ関係`に再アンカーし、`クロコ関係`直下を`git init`（コミットは本人の依頼を受けて実施、内容は本ファイル参照）。`クロコ本体`配下の`.claude`はツール状態であり本体の成果物ではないため`.gitignore`で除外。`クロコ関係`直下・`クロコ本体`内にできていた重複Obsidian設定は本人が削除済み（旧`プログラミング関係\クロコ`側の扱いは未確認のまま、上記の通り本人の手動対応待ち）。

第一段階のパイプラインを実装・実地検証する過程で表面化した論点をここにまとめる。
**解決済みのものも記録する**（同じ調査を繰り返さないため）。未解決のものは4章にも再掲する。

### A. 仕様の更新（2.5章の確定事項を変更したもの）

1. **Geminiのモデルを 3.5 Flash → `gemini-3.6-flash` に変更（確定）**。
   実装時に調べ直したところ、現行GAのFlashが3.6になっていたため本人判断で更新。
   `.env` の1行で切り替えられるようにしてある。
2. **Inbox DBに「試行回数」(number) を追加（確定）**。
   2.5章-12の「再試行の上限を超えたら要確認に落とす」を実装するには
   回数を数える場所が必要だったが、10.の表に該当する列が無かったため。
3. **種別に「資料」を追加（確定）**。選択肢は アイデア / 予定 / 資料 の3つになった。
   → 経緯は下記 B-1。
4. **「予定日」は種別が「アイデア」でも、日付が取れていれば記録する（確定）**。
   当初は種別＝予定のときだけ入れていたが、それだとGeminiが種別を誤ったときに
   抽出できていた日付ごと消える。カレンダービューは種別で絞るので、
   入っていても表示は乱れない。情報を捨てない方針を優先した。
5. **ステータスに「対象外」を追加（確定）**。選択肢は 未処理 / 処理中 / 完了 / 要確認 / 対象外。
   種別が予定・資料のものは着手されようがないので、捕捉時点でこれにする。
   「未処理」は着手待ちのフラグとして機能しているため、そこに残すとキューが濁る。
6. **着手アイテムの選択（確定・追加）**。候補が複数あるとき、画面があれば一覧を出して
   選べるようにした。ただし起動時に無人で走る前提なので待ち続けてはならず、
   制限時間（既定60秒、`CROCO_PICK_TIMEOUT`）を過ぎたら先頭で自動的に進む。
7. **終了時のまとめ表示（確定・追加）**。「要確認」はNotionを見に行かないと気づけず
   放置されうるため、実行の最後に必ず画面へ出す（件数と、要確認・処理中の一覧）。
   ランチャも常に `pause` してウィンドウを残す。
8. **クロコは対話モードで起動する（確定・方針変更）**。
   当初は `claude -p`（非対話）で完全に無人実行する設計だったが、これを変更する。
   - **理由**：非対話だと、変な方向に進み始めても終わるまで口を挟めない。
     初回の実地テストでも、進行中の様子を外から確認するしかなかった。
     途中で軌道修正できることの価値が、完全無人であることの価値を上回る、という判断。
   - パーミッションは引き続き自動承認（`--permission-mode auto`）なので、
     本人が離れていても勝手に進む。**「無人でも動く」ことは失っていない。**
     変わったのは「見ていれば介入できる」ようになったこと。
   - 実装上は、標準入出力を横取りせずクロコに明け渡す（横取りするとTUIが壊れる）。
     そのぶんログファイルにクロコの発言は残らないが、
     セッション自体はClaude Code側に残るので `claude --resume` で追える。
   - 非対話も `--headless`（または `CROCO_INTERACTIVE=0`）で残してある。
   - **副作用として認識しておくこと**：対話セッションは本人が終えるまで終わらない。
     起動したまま離席すると、まとめ表示まで進まず、二重起動ロックも保持されたままになる。
9. **使ったトークンの記録（確定・追加）**。Claude Pro には利用量の上限があるため、
   1タスクにどれくらい使ったか・これからどれくらい使いそうかを見えるようにする。
   - 対話モードでは出力を横取りできないので、Claude Codeがローカルに残す
     セッション記録（`~/.claude/projects/.../*.jsonl`）から実測値を読む。
     記録の特定はディレクトリ名のエンコード規則ではなく、中の `cwd` の照合で行う
     （命名規則に依存すると仕様変更で黙って壊れるため）。
   - アイテムごとに Inbox DB の「トークン」列へ積み上げる。
     着手アイテムの選択画面と終了時のまとめで、過去の実績と見込みを出す。
   - **数え方**：「新しく処理されたトークン」（入力＋出力＋キャッシュ書き込み）を基準にする。
     キャッシュ読み込みは含めない。会話が長引くだけで際限なく膨らみ、しかも大幅に割安に
     扱われるため、混ぜると「何をどれだけやったか」の指標にならなくなる。
   - **できないこと**：プランの残量は取得できない。分かるのは実績だけで、
     残りいくつ使えるかはクロコのセッション内で `/usage` を叩く必要がある。
   - 「後でこのデータを解析して研究用プロジェクトの参考にするかもしれない」（2.5章-10）
     という動機にも、コストという軸が1本増える形で効く。
10. **1回の起動で複数アイテムを処理する（確定・変更）**。当初は「起動につき1件」だったが、
    1件終わるたびにPCを再起動しないと次に進まないのは実態に合わないため、
    セッションが終わったら次のアイテムへ続けて進む形にする。
    - **上限は必須**（既定3件 / `CROCO_MAX_ITEMS`）。無制限だと離席中にプランの
      使用枠を使い切りうる。`CROCO_TOKEN_BUDGET` でトークン量の上限も置ける
      （既定0＝無制限。アイテムの途中では止まらず、次を始めるかの判断にだけ使う）。
      `CROCO_MAX_ITEMS=0` は「捕捉だけして実装はしない」の逃げ道。
    - **止める条件は4つ**：対象が尽きた／件数の上限／トークンの上限／異常終了・中断。
      異常終了で続けないのは、同じ原因で残りも失敗して試行回数だけを食う公算が高いため。
    - **同じ起動の中で同じアイテムを二度は処理しない**。セッションを終えても「完了」に
      ならなかったものは「処理中」のまま残り、並び順では最優先されるので、
      除外しないと同じアイテムを延々と起動し続けて試行回数だけが上限まで増える。
      次回の起動では通常どおり最優先で再開される（2.5章-10の方針は変えていない）。
    - 継続の可否は本人に聞くが、無人前提なので**既定は「進む」**（時間切れで続行）。
    - 副次的に見つけて直したこと：制限時間つきの入力を「ブロックする readline を
      デーモンスレッドで待つ」形で実装していたが、時間切れ後もそのスレッドが stdin を
      掴んだまま残り、直後に起動する対話モードのクロコと入力を奪い合っていた。
      本人の最初のキー入力が吸われる壊れ方をする。キー入力の有無を見ながら
      自前で1行を組み立てる形（`msvcrt.kbhit`）に変更した。

11. **クロコ自身への改修依頼の扱い（確定・追加）**。「クロコのdispatchを直して」のような
    依頼を、捕捉の分類で「要確認」に隔離する（自己推薦書と同じ経路）。
    - **前提**：クロコはクロコ本体を書き換え**られない**。`croco_settings.json` の deny に
      `Edit(**/クロコ本体/**)` と `Write(**/クロコ本体/**)` があり、deny はどのパーミッション
      モードでも効く。**この制限は外さない**。deny リスト自体がクロコ本体にあるため、
      書けるようにすると自分の拘束を自分で外せる。読むのは可能（改修案までは書ける）。
    - **隔離する理由は認知コストではなく無駄の削減**。隔離しなくても最終的には「要確認」に
      落ちる（denyで詰まる→試行回数の上限）。ただしそれは3セッション分のトークンを
      使ったうえ、理由が「試行回数が上限に達した」という**誤った説明**で残る。
      隔離は「要確認を増やす」のではなく、**同じ着地を即座に・正しい理由で**もたらす。
12. **保留理由の記録（確定・追加）**。「要確認」に落とした側が理由を必ず残す
    （Inbox DBに select 列「保留理由」を追加）。
    - **動機**：11の検討中に本人が「要確認が増えると認知コストが上がらないか」と指摘。
      調べると、当時の「要確認」7件は**全件が同一の定型文**
      （「本人自身の対応が必要と判定したため、着手せず要確認にした」）で、
      まとめを見ても何で止まっているか分からない状態だった。
      増やす前から既に山になっていたので、そちらを先に直す。
    - 値は7種類。捕捉時にGeminiが判定する4つ（本人名義の文書／現実世界の行動／
      クロコ自身の改修／本人の判断）＋「なし」＋クロコ側で付ける2つ
      （試行回数の上限／クロコからの相談）。
    - Geminiの出力は `needs_human`（真偽値）から `human_reason`（enum）へ変更。
      真偽値＋理由の2フィールドにすると矛盾した状態を持ててしまうため、1つにまとめた。
      **欠落・不正値は「なし」以外へ倒す**（「なし」に倒すと自動着手されるため）。
    - まとめでは理由ごとに束ね、「で、何をすればいいのか」を1行添える。
      理由が空のものは既知の理由に混ぜず「（理由の記録なし）」として別に出す
      （分からないものに嘘のラベルを貼ると束ねる意味がなくなるため）。
    - **分類に対処法の1行が書けない＝分類として機能していない**、という基準で選択肢を決めた。
      この対応関係はテストで縛ってある。

13. **本人名義の文書を、どこまで手伝わせるか（確定・従来より緩和）**。
    従来は「本文は書かない」としか決めておらず、**添削・相談の可否が未定**だった。
    本人の判断で「下書きを読んでの指摘まではやってよい」に確定（2026-07-25）。
    - **してよい**：下調べ、必要書類の洗い出し、要件の整理（字数制限・締切・必須項目）、
      構成・骨子の相談、原稿を読んでの指摘（どこが・なぜ）。
    - **してはいけない**：本文そのもの。書き出し例・言い換え案・清書・
      「こう直すといい」という文章の提示を含む。文は本人が書く。
    - **要件はクロコに書かせてよい**（本人の判断）。「800字以内」は本文ではなく要件なので、
      AI作成が問題になる対象に当たらない。
    - **実装は場所で分ける**。`クロコ管轄プロジェクト/下書き/` を本文置き場とし、
      deny に `Edit(**/下書き/**)` `Write(**/下書き/**)` を追加。読むのは自由。
      要件は `下書き/` の外に置くのでクロコが書ける。
      指摘の中身はプロンプトで縛るしかないが、**文章を書き込む行為自体は
      deny で物理的に止まる**ので、最悪の踏み外しは起きない。
    - **書く側の道具**：本人が以前 Claude に作らせた文字数チェッカー
      （`プログラミング関係\Twitter-like-char-counter.html`）を下書きエディタに拡張して使う。
      CLIのクロコを相談相手に、横のブラウザで本人が書く、という形。
      **アプリを分けること自体が線引きになる**（クロコの出力から本文への経路が、
      本人が読んで自分で打つ以外に存在しない）。
      追加した機能：自動保存、複数文書、ファイルの読み書き（File System Access API、
      非対応時はダウンロードに退避）、Markdownプレビュー、Markdown記法を除いた字数カウント、
      要件ペイン（クロコが書いた要件ファイルを読み込んで横に置ける）。

14. **相談フェーズの追加（確定・新規）**。「要確認」から**着手キューに戻る経路が無く**、
    落ちたものが溜まる一方だった。まとめを出した直後に「今ここで話すか」を聞き、
    選ばれたら相談用のプロンプトでクロコを起動する。
    - **なぜクロコ側でやるか**（Notion AI／第二段階のGeminiプロキシと比較して確定）：
      (a) 話した結果をそのまま実装に繋げられるのはクロコだけで、Notionだと
      「次回起動待ち」の継ぎ目が残る。(b) 判断材料が `クロコ管轄プロジェクト` の
      ファイル側にあり、Notion AIからは読めない。(c) 要確認は定義上「判断が要るもの」で、
      Geminiは狭く安いタスク専用という使い分けの方針と真逆になる。
      (d) 本人名義の文書は「相談」と「代筆」の境界が滑りやすく、Notion AI側には
      deny もプロンプトの線引きも無いので、隔離の仕組みを自分で迂回することになる。
      → **Notion側に残す役割は「短い答えを書き置く」ことだけ**（検討は持たせない）。
    - **既定は実装フェーズと逆で「話さない」**。実装は無人前提なので時間切れなら続行するが、
      相談は本人が居ないと成立せずトークンも食う。時間切れなら黙って終わる。
    - **猶予は着手の選択（60秒）より短く20秒**（`CROCO_CONSULT_TIMEOUT`、0で無効）。
      着手の選択は候補が複数あるときだけ出るが、相談は「要確認」が1件でもあれば出る＝
      ほぼ毎回出る。しかも全処理が終わったあとなので、待ち時間が丸ごと死に時間になる。
    - **`resume` は保留理由を消さない**。「なぜ人が要ったか」は仕事の性質でもあり、
      戻したあとの着手でも線引きに使う。試行回数だけは0に戻す（相談で止まった回は失敗ではない）。
    - **副作用として塞いだ穴**：保留理由を残すと、戻ったアイテムは形の上では
      実装プロンプトの「着手してはいけないもの」に当たる。何もしないと
      **resume と review を往復し続ける**ので、「相談済みなので改めて review に
      回さなくてよい（ただし線引きは守る）」という但し書きを自動で差し込むようにした。
15. **本人名義の文書を選んだら下書きエディタを自動で開く（確定・追加）**。
    クロコはCLIで文章を書く場所にならない。書くのは本人・相談相手がクロコ、という
    分担なので、書く場所を人手で探させない。`CROCO_EDITOR_PATH`、無ければ何もしない。
    - **2026-07-26、初めて実際に動かして開き方を全面的に作り直した。**
      当初の `os.startfile` は「既定のブラウザで開く」つもりだったが、
      **`.html` の関連付けはVS Codeが握っていて、ソースが表示されるだけだった**。
      拡張子ではなく `https` の既定ハンドラから既定ブラウザを引く形に変更。
    - 本人の要望で、さらに3点を確定。**普段のログイン済みブラウザに混ぜない**

### 参考資料：ブレスト用対話AIアーキテクチャ（第二段階向けの調査メモ）

第二段階（スマホからの対話ブレスト部分）を作る際の参考として、一般的な会話AIアーキテクチャを調査済み（2026年7月時点）。

- 音声を使う場合の基本形：**STT（音声→テキスト）→ LLM → TTS（テキスト→音声）**のパイプライン。
- より新しい方式：STT/TTSを分けず、音声を直接入出力できる**統合Audio LLM**を使う構成もあり、レイテンシが小さい。
- **Function calling**：LLMが会話の中で「これはメモとして保存すべきか」等を自分で判断し、ツール（DB書き込み等）を呼び出す設計。
- **ハイブリッド型**：明確な意図は決め打ちのハンドラで処理し、曖昧なものだけLLMに投げることで、コストと精度を両立させる設計。

### 3層アーキテクチャ

1. **スマホ（指示・閲覧の窓口）**
   - 役割：すべての指示入力の入口。外出先からも操作。
   - 主なツール：Dify (PWA)
   - 閲覧：予定はNotion（カレンダー画面）で確認

2. **ラズパイ（常時起動ハブ：日常タスク＋ログ蓄積）**
   - 役割：日常タスク（例：PDFリンク等からのスケジュール抽出→登録）を自動処理／プロジェクト開発用のブレストログ・仕様書（Markdown）を蓄積・同期
   - 主なツール：Dify (OSS)、Gemini API、Docker / Docker Compose、Cloudflare Tunnel（外部から安全にアクセス）、Syncthing（PCへ暗号化同期）
   - 方針（クロコ3準拠）：メモリ節約のため、**ラズパイ側でのClaude Code運用は除外**する。

3. **PC（本丸開発：Claude Code実行環境）**

   - 主なツール：Claude Code（Anthropic公式CLI）、Node.js / npm

### データの流れ（ワークフロー）

1. スマホ（Dify）：移動中にアイデア出し・壁打ち（ブレストログ生成）
2. ラズパイ（Dify + Gemini）：セッションを要約し、Markdownの「指示書/仕様書」としてローカル保存

4. PC（Claude Code）：同期された.mdを最優先コンテキストとして読み込み、実装開始
